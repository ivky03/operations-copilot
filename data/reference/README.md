# Reference Dataset: Brindlewood Home (synthetic)

**All data here is synthetic.** Brindlewood Home is a fictional home-goods retailer. No real company, customer or transaction is represented.

This dataset exists so that evaluation questions can have **exact, verifiable answers**. It is small enough to check by hand, and it deliberately includes the cases that trip up question-answering systems. The engine itself is domain-agnostic; this is one reference domain.

## Contents

| Path | What |
|---|---|
| `tables/*.csv` | Four tables, generated by `backend/datagen` (seeded, byte-for-byte reproducible) |
| `manifests/*.yaml` | One manifest per table: column types and meanings, relationships, value aliases, governed metric definitions |
| `documents/*.md` | 11 policy and reference documents (12 files; one document has two versions) |
| `access.yaml` | Initial group → source grants (kept apart from manifests: stewards describe data, administrators grant access) |

| Table | Rows | Grain |
|---|---|---|
| `stores` | 8 | One row per store or web shop |
| `products` | 25 | One row per product |
| `transactions` | 430 | One row per invoice line, Jan–Apr 2026, including cancellation lines |
| `returns` | 24 | One row per returned invoice line |

Regenerate with `cd backend && uv run python -m datagen`. A test fails if the committed files drift from the generator.

## Deliberate edge cases

| Case | Where | Why it matters |
|---|---|---|
| Cancellations as separate negative lines (`C` prefix) | transactions | Naive sums double-count or miss them |
| An order placed 28 Feb, cancelled 1 Mar | transactions | Cancellations count in the month they happen; Ireland's March net sales are negative |
| Order at 23:47 on 31 Mar | transactions | Month-boundary timestamp |
| ~20% of orders have no customer ID | transactions | Guest checkouts, not errors |
| France launches 2 Mar 2026 | stores | No French sales in Jan/Feb by design |
| Glass Vase discontinued 28 Feb | products | No sales from March |
| SPRING10: 10% off Textiles in April | transactions | Selling price ≠ list price |
| Three "desk lamp" products, two "oak table" products | products | Ambiguous references need clarification |
| Country aliases (UK, Holland, …) | manifests | Value grounding |
| Returns policy v1 (14 days) superseded by v2 (30 days) | documents | Outdated policies; version-aware citation |
| Finance-only and Operations-only documents | documents, access | Permission boundaries |
| Two returns without a reason | returns | Missing values |
| No cost, margin, web-traffic or satisfaction data | all | Questions the data cannot answer |

## Metric definitions

Defined in `manifests/transactions.yaml` and `manifests/returns.yaml`, and described for humans in `documents/metric-definitions.v1.md`:

- **Gross sales** = Σ quantity × unit price on sales lines
- **Cancellation value** = value of cancellation lines, counted in the month of cancellation
- **Refund value** = Σ refund amount, counted in the month of refund
- **Net sales** = gross sales − cancellation value − refund value
- **Orders**, **average order value** (gross sales ÷ orders), **cancellation rate** (cancelled orders ÷ orders)

## Evaluation set

`evals/golden/stage_a.yaml` holds 45 cases across eight categories: calculation, value grounding, policy, combined, ambiguous, unanswerable, permission and follow-up.

Expected numbers are **not** written by hand. Each case declares a query, and an independent pandas oracle (`backend/evals/oracle.py`), which shares no code with the application, computes the answers into `stage_a.expected.json`. A validator checks the set itself: citations exist, personas can read what they must cite, clarification options exist. Tests confirm the validator rejects deliberately broken cases.
